Two sets of measurements, both from Hardcharger's repository (`bench/`,
[`docs/benchmarks.md`](https://github.com/gizmodata/hardcharger/blob/main/docs/benchmarks.md)),
both against GizmoSQL, Hardcharger's predecessor, with the same data. Numbers are medians. Every
run checked its results (row counts and column sums), so a fast wrong answer can't count.

<Aside type="note" title="How to read these">
Benchmarks measure one setup on one day. Spot instances vary, and so does your network. The
method is here so you can run the same thing on yours.
</Aside>

<Aside type="caution" title="Derived from TPC-H">
The workloads are derived from TPC-H: the 22 queries' text (`tpch_queries()`) and the data
(`dbgen`, scale factor 1 or 10; `lineitem` alone for the transfer and load runs) come from
DuckDB's `tpch` extension. They deviate from the TPC-H specification throughout: no refresh
functions, no power or throughput test, no audit, the query text as DuckDB's extension has it
(fixed substitution parameters), and timings that include moving every row to the client.
Derived from the TPC-H benchmark; not an official TPC-H result and not comparable to published
TPC-H results, as these results do not comply with the TPC-H specification. TPC-H™ is a
trademark of the Transaction Processing Performance Council (TPC).
</Aside>

## Summary

On one machine (Apple M5 Max, loopback, no TLS):

| Workload | Hardcharger | GizmoSQL 1.41 | |
|---|---:|---:|---:|
| The 22 queries derived from TPC-H, SF10 | **832 ms** | 1,201 ms | **1.44× faster** |
| Fetch 10M rows (1.73 GB of Arrow) | **0.83 s** | 1.32 s | **1.59× faster** |
| 10 concurrent clients | **39.0 queries/s** | 21.9 queries/s | **1.8× the throughput** |
| 10 concurrent clients, p95 latency | **471 ms** | 1,328 ms | **2.8× lower** |

Over a real network: two AWS c8gn.8xlarge machines, TLS on both servers, median of five runs:

| Workload | Hardcharger | GizmoSQL 1.42 | |
|---|---:|---:|---:|
| Fetch SF10 lineitem (60M rows, 10.5 GB of Arrow) | **0.97 s** | 15.2 s | **15.7× faster** |
| Fetch SF1 lineitem (6M rows) | **0.148 s** | 1.74 s | **11.7× faster** |
| Fetch 100M narrow rows | **0.45 s** | 5.43 s | **12.0× faster** |
| Fetch SF1 lineitem across regions (46 ms away) | **1.96 s** | 12.26 s | **6.3× faster** |
| Load SF10 lineitem (bulk ingest, 8 upload parts) | **3.00 s** | 9.44 s | **3.1× faster** |
| Load SF1 lineitem across regions (8 upload parts) | **2.91 s** | 13.94 s | **4.8× faster** |

The network fetches above read the result in partitions (32 on the LAN, 8 in order across
regions) and the loads send 8 parts at once; [the performance model](/concepts/performance-model/)
explains why that matters.

- Part of the gap is the engine: Hardcharger beats even in-process DuckDB 1.5.6 (832 against
  1,016 ms), so DuckDB 2.0 is faster on these queries before any protocol is involved (Q01, Q19
  and Q21 most of all).
- GizmoSQL adds about 185 ms over in-process DuckDB across the 22 queries (about 8 ms a query:
  gRPC, Flight's two round trips, and the server's per-statement work). Hardcharger's one-round-trip
  path answers small queries within about a millisecond of in-process DuckDB 1.5.6 (Q11: 6.1
  against 5.2 ms) while running a different engine.

### Ten clients at once

`bench/concurrency.py`: ten clients, each with its own connection and session, each running Q01,
Q03, Q06, Q10, Q14 and Q19 six times (360 queries), same machine and data:

| | Throughput | Median latency | p95 latency |
|---|---:|---:|---:|
| Hardcharger | 39.0 queries/s | 223 ms | 471 ms |
| GizmoSQL 1.41 | 21.9 queries/s | 277 ms | 1,328 ms |

## Over a real network (AWS, 2026-10-17)

Moving large results to a client, and bulk-loading a client's Arrow table, from a second machine.
Scripts: `bench/remote/` (provisioning, server start, client harness, summarizer); raw results:
`bench/remote/results/2026-10-17-throughput/`.

### Setup

- **Machines:** c8gn.8xlarge (Graviton4, 32 vCPU, 64 GiB, 100 Gbit/s), Ubuntu 24.04 arm64,
  Spot. **LAN:** server and client in one placement group in us-east-2c (RTT 0.09 ms; iperf3: 1
  stream 9.5 Gbit/s, 16 and 32 streams 99.8 Gbit/s). **WAN:** a third machine in us-west-2c
  (RTT 46 ms), with Ubuntu's default TCP buffers, as a client usually has.
- **TLS on both servers**, one self-signed P-256 certificate, TLS 1.3. `threads=32`,
  `memory_limit=40GB`, the same database file in `/dev/shm`.
- **Hardcharger:** the `hardcharger-linux-arm64` CI artifact after the transfer work (now on
  `main`), default settings (122,880-row batches, `max_result_partitions` 32). Client:
  `adbc-driver-warpsql`. "n partitions" rows set `adbc.warp.statement.result_partitions` = n and
  `result_order` = `any` or `preserve` ("in order"). **GizmoSQL** 1.42.0 (DuckDB 1.5.6) through
  `adbc-driver-gizmosql` 2.0.15. "Hardcharger 0.2.0" is the release before the transfer work,
  same method.
- **Fetch:** `SELECT * FROM <table>`, drained as Arrow batches. **Ingest:** `adbc_ingest(mode="create")`
  of lineitem from client memory. Every fetch is checked in full (row count and three column sums
  against the server's), and every ingest afterwards.
- One warm-up, then 5 measured repetitions; median, p10 and p90. "Wire MB" is what crossed the
  client's network interface, TLS included. Client and server cores are CPU time over wall time.

### Reading the numbers

- **One TLS stream now runs at the network's per-flow limit, like plaintext.** SF10 lineitem
  over TLS took 8.760 s (1.18 GB/s of Arrow, 9.5 Gbit/s on the wire), against 8.747 s over
  plaintext and 21.170 s before the transfer work.
- **Partitions go past one flow.** With 32 partitions SF10 took 0.971 s (10.7 GB/s of Arrow,
  86 Gbit/s on the wire). Order costs nothing on the LAN: interleaved partitions were as fast as
  any-order ones.
- **8 partitions beat 16, and 32 beat both** (SF10: 1.43, 1.59 and 0.97 s). The server was never
  the limit; the client's reading was. Why 16 did worse than 8 is not understood yet.
- **Ingest went from 10× slower than GizmoSQL to as fast or faster.** SF1: 1.30 s (GizmoSQL 1.61 s,
  before 10.20 s); SF10: 9.34 s (GizmoSQL 9.43 s, before 102.5 s). Plaintext ingest is no longer
  slower than TLS.
- **zstd is for slow links.** On the LAN, zstd fetch is slower than none (SF10: 13.5 s against
  8.8 s: the client decompresses on 1.5 cores), and zstd ingest much slower (27.7 s: the Go driver
  compresses on one core). Over the WAN, zstd on one stream is 3× faster than none (4.05 s against
  12.64 s).
- **WAN: partitions win, one stream doesn't.** SF1 across regions with 8 partitions in order:
  1.96 s (GizmoSQL 12.26 s). One stream: 12.64 s, the same as GizmoSQL, bound by the 4 MB
  `tcp_wmem` limit at 46 ms. 32 partitions in order over the WAN was erratic (median 27.7 s,
  p10 4.8 s): interleaving waits for the slowest of 32 long-distance flows. Use 8, or any order.

### Where Hardcharger still lost (before partitioned uploads)

- **Ingest over a fast LAN**: Warp SQL's ingest was one upload on one connection, so SF10 couldn't
  beat the 9.5 Gbit/s flow limit (9.34 s); a protocol that splits one upload over many
  connections loaded it about 3× faster. [Partitioned uploads](#partitioned-uploads-2026-10-17)
  closed that gap.
- **Bytes on the wire.** Arrow IPC is not the most compact encoding: a more compact wire format
  sent about 30% fewer bytes for lineitem in the same tests.
- **One stream across a WAN**: as slow as GizmoSQL whenever the client doesn't ask for
  partitions. The drivers now ask for 8 by default.
- **zstd over fast links**, on the client side (one core compresses or decompresses in the Go
  driver).

### What was not equal

- GizmoSQL runs DuckDB 1.5.6; Hardcharger runs DuckDB 2.0. Both read the same file format.
- The ADBC ingest clients sent the source batches as they were (122,880 rows, about 21 MB). The Go
  Flight SQL client refuses gRPC messages over 16 MiB by default, so GizmoSQL's client was given
  `adbc.flight.sql.client_option.with_max_msg_size` = 1 GiB.
- Only Hardcharger compresses (zstd); GizmoSQL's driver has no compression option.
- Over the WAN only SF1 was measured. Tuned TCP buffers would raise every one-stream number there.
- Spot instances and one placement group, on one day. Most configurations were stable (p90 within
  a few percent of the median).

## Partitioned uploads (2026-10-17)

Two changes since the runs above, measured on fresh VMs with the same scripts:

1. **Partitioned ingest** (Warp SQL §8.3, capability `partitioned_ingest`): the client opens one
   ingest, sends its upload as N parts at once, each over its own connection, and commits them as
   one. The server reads every part through one reader, so DuckDB inserts from all of them in
   parallel, in one transaction. All or nothing; rows land in no defined order. The ADBC driver
   (`adbc.warp.ingest.parts`) uses 8 parts for uploads of two batches or more.
2. **Split results by default**: the ADBC driver and the `hardcharger` CLI ask for up to 8
   partitions, in order. Results of fewer than two batches stay one stream.

Same setup as above (c8gn.8xlarge, LAN in one placement group, WAN across regions, TLS,
`threads=32`). Hardcharger with default settings; "Warp SQL" rows set `adbc.warp.ingest.parts`

- **Ingest is 3× faster than one stream on the LAN** (SF10: 9.14 s to 3.00 s) and nearly 5×
  across regions (SF1: 14.0 s to 2.9 s).
- **The LAN SF10 load is now bound by DuckDB's insert, not the network**: the server used 24.8
  cores for 8 parts and 25.7 for 16, and 16 parts were no faster than 8.
- **The split-results default pays off on any link**, with no option set: LAN SF1 fetch 0.90 s
  to 0.17 s, SF10 8.76 s to 1.38 s, WAN SF1 14.0 s to 2.30 s.

### Where Hardcharger still loses

- **LAN SF10 ingest**, by 5 to 12% to a protocol whose client opens many more connections:
  both are bound by DuckDB's insert on the server, and Warp SQL's wire format is 23% larger
  for lineitem.
- **WAN SF1 ingest**, by 20 to 35% to the same protocol with 8 parts; 16 parts come closer.
- **SF10 fetch at the default 8 partitions** is 62% slower than the fastest result measured;
  32 partitions took 0.97 s in the section above. The default stays 8, which suits the WAN
  better.
- **Ordered bulk loads** stay on one stream (9.14 s for SF10 on the LAN).

### Reproducing

```bash
set -a; . <AWS credentials .env>; set +a
bench/remote/provision.sh lan                 # server + LAN client (and `wan` for the WAN client)
# copy bench/remote/*, the TLS cert/key, the Hardcharger tarball (server) and the
# adbc_driver_warpsql wheel (clients) to ~/bench on each VM, then on each:
bash ~/bench/setup-vm.sh server|client
~/venv15/bin/python ~/bench/gen_data.py --path ~/bench/base.duckdb     # server
~/venv/bin/python ~/bench/prepare_data.py --data-dir ~/bench/data      # clients
nohup python3 ~/bench/cpu_log.py --out ~/bench/cpu-server.log &        # server
bench/remote/run_matrix.sh lan                # then: run_matrix.sh wan
python3 bench/remote/summarize.py --results results-lan.jsonl results-wan.jsonl --cpu cpu-server.log
bench/remote/provision.sh down                # terminate and delete everything, then verify
```

Cost: about 1.3 hours of three Spot c8gn.8xlarge (about $0.35/h each) and about 25 GB across
regions: about $2. Every resource was tagged `Purpose=hardcharger-benchmark` and deleted.
