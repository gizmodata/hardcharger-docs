Hardcharger's access control keeps users, roles and grants in a PostgreSQL database that every
replica of a cluster shares, and you manage them in SQL. Each statement is checked inside
DuckDB against its own plan, after binding and again before optimizing, so nested SQL, views
and macros can't route around a grant. Anything the check can't classify is refused.

## Turn it on

Point [`rbac_store_uri`](/reference/configuration/#rbac_store_uri) at a PostgreSQL database.
Hardcharger creates its tables in the schema `hardcharger_rbac` there:

```bash
HARDCHARGER_ADMIN_PASSWORD='change-me' \
HARDCHARGER_RBAC_STORE_URI='postgresql://hardcharger:secret@db.internal:5432/hardcharger' \
  hardcharger-server --database analytics.duckdb
```

The URI is `postgresql://user:password@host[:port]/database`, or a libpq string such as
`'host=db.internal dbname=hardcharger user=hardcharger'`. Every replica names the same database;
changes reach all of them within about a second.

### A DuckDB file, for one server

Use PostgreSQL in production, and for any cluster of more than one replica. For development, or
a server that will only ever run as one replica, the store can be a DuckDB file of its own
instead: `duckdb:` and a path, or any path ending in `.duckdb`.

```bash
HARDCHARGER_ADMIN_PASSWORD='change-me' \
HARDCHARGER_RBAC_STORE_URI='duckdb:/var/lib/hardcharger/rbac.duckdb' \
  hardcharger-server --database analytics.duckdb
```

- The file and its write-ahead log are created `0600`, and each change is checkpointed into the
  file at once. An existing file that other users of the
  host can read or write is refused at startup (`chmod 600` it), and so is a store file that is
  also the database, the instrumentation or the log file.
- One server per file: a second server on the same file stops at startup, saying the DuckDB store
  serves a single server and to use PostgreSQL for several replicas.
- The file holds password hashes and grants, so no SQL reaches it, the administrator's included,
  however the path is written or computed (see [the server's own files](/concepts/security-model/#guards-that-apply-to-everyone)).
- There is no migration between the two stores: moving to PostgreSQL later means creating the
  users, roles and grants there again.

With the store in `rbac.duckdb`, not even the administrator can read it in SQL, and a second server
on the same file stops at startup:

```console test profile=rbac_duckdb exit=1
$ HARDCHARGER_PASSWORD='change-me' hardcharger --host localhost --tls=false --username hardcharger \
    --command "SELECT count(*) FROM read_blob('rbac.duckdb')"
Error: Permission Error: Permission denied: Hardcharger blocked access to 'rbac.duckdb' (the access-control store). It is one of the server's own files, which no SQL may open, read or write, whatever the role.

LINE 1: SELECT count(*) FROM read_blob('rbac.duckdb')
                             ^^^^^^^^^^^^^^^^^^^^^^^^
```

```console test profile=rbac_duckdb exit=1
$ HARDCHARGER_ADMIN_PASSWORD='change-me' hardcharger-server --port 31400 --health-port 31401 \
    --database other.duckdb --rbac-store-uri duckdb:rbac.duckdb
…
… A DuckDB store serves a single server; for several replicas, use a PostgreSQL store (rbac_store_uri: postgresql://...)
```

<Aside>
The administrator (`--admin-username`, `hardcharger` by default) is a superuser and is never
subject to grants. Everyone else should be a store user. A store user's name can't be the
administrator's.
</Aside>

## Users and roles

The rest of this page runs as the administrator. Create some data, a role, and a user in it:

```sql test profile=rbac
CREATE SCHEMA analytics;
CREATE TABLE analytics.orders AS
  SELECT * FROM (VALUES (1, 'EU', 120.0), (2, 'US', 80.0)) t(id, region, amount);
CREATE TABLE main.customers AS
  SELECT * FROM (VALUES (1, 'ann@example.com', '1990-01-02'), (2, 'bob@example.com', '1985-07-08')) t(id, email, birthday);
```

```sql test profile=rbac
CREATE ROLE analyst;
GRANT SELECT ON SCHEMA analytics TO analyst;               -- every table there, now and later
GRANT SELECT (id, email) ON main.customers TO analyst;     -- two columns only
CREATE USER joe WITH PASSWORD 'joe-secret';
GRANT analyst TO joe;
```

Access-control statements run one at a time: send each as its own statement (the CLI and the
drivers do, one per `;`).

Now sign in as `joe`. What he may read works; what he may not is refused, with the reason:

```python test profile=rbac
from adbc_driver_hardcharger import dbapi as hardcharger

with hardcharger.connect(uri="hardcharger://localhost?tls=false", username="joe", password="joe-secret") as conn:
    with conn.cursor() as cur:
        cur.execute(operation="SELECT sum(amount) AS total FROM analytics.orders")
        print(cur.fetchone())
        cur.execute(operation="SELECT id, email FROM main.customers ORDER BY id")
        print(cur.fetchall())
        try:
            cur.execute(operation="SELECT birthday FROM main.customers")
        except hardcharger.ProgrammingError as e:
            print("refused:", e)
```

```text output
(Decimal('200.0'),)
[(1, 'ann@example.com'), (2, 'bob@example.com')]
refused: UNAUTHORIZED: [chargewire] ExecuteQuery: Permission Error: Hardcharger blocked this statement: user joe has no SELECT on column(s) birthday of my.main.customers. Access control on this server lets user joe do only what their roles are granted (see SHOW GRANTS) (permission_denied, HTTP 403, request …). SQLSTATE: 42501
```

## Privileges

| Privilege | On |
|---|---|
| `SELECT` (optionally on columns: `SELECT (a, b)`) | a table or view, a schema, a catalog |
| `INSERT`, `UPDATE`, `DELETE` | a table, a schema, a catalog |
| `MAINTAIN` (`ANALYZE`, `VACUUM` of a table; see [Maintenance](#maintenance)) | a table, a schema, a catalog |
| `CREATE TABLE`, `CREATE VIEW`, `DROP TABLE`, `DROP VIEW`, `ALTER TABLE`, `ALTER VIEW` | a schema or catalog |
| `CREATE MACRO`, `DROP MACRO` (scalar and table macros; see [Macros](#macros)) | a schema or catalog |
| `CREATE TYPE`, `DROP TYPE` (enums, structs, aliases; see [Types](#types)) | a schema or catalog |
| `CREATE TRIGGER`, `DROP TRIGGER` (on a table the role owns; see [Triggers](#triggers)) | a schema or catalog |
| `USAGE` (`nextval()`, `currval()`; see [Sequences](#sequences)) | a sequence (`ON SEQUENCE`), a schema, a catalog |
| `CREATE SEQUENCE`, `DROP SEQUENCE` (`DROP SEQUENCE` also allows `setval()`) | a schema or catalog |
| `CREATE SCHEMA`, `DROP SCHEMA` | a catalog, or a schema for the schemas nested in it (see [Nested schemas](#nested-schemas)) |
| `EXECUTE` (calling a table function; see [Table functions](#table-functions)) | a table function (`ON TABLE FUNCTION name`) |
| `ALL [PRIVILEGES]` | a table, a schema, a catalog: every privilege above that applies there (never `EXECUTE`) |

`ALL` means all of them. On a table it is `SELECT`, `INSERT`, `UPDATE`, `DELETE` and `MAINTAIN`; on a schema,
those, `CREATE`, `DROP` and `ALTER` `TABLE` and `VIEW`, `CREATE` and `DROP` `MACRO`, `TYPE` and `TRIGGER`,
`USAGE`, `CREATE SEQUENCE` and `DROP SEQUENCE`, and `CREATE SCHEMA` and `DROP SCHEMA` for the schemas nested in
it, so a role can build in that schema; on a catalog, all of that. `GRANT ALL` is stored as the separate
privileges it stands for (`SHOW GRANTS` lists each), and `REVOKE ALL` takes back the same set.

```sql test profile=rbac
CREATE ROLE loader;
GRANT SELECT, INSERT ON TABLE analytics.orders TO loader;
GRANT ALL PRIVILEGES ON SCHEMA analytics TO loader;
GRANT CREATE SCHEMA, SELECT ON CATALOG my TO loader WITH GRANT OPTION;   -- the catalog of my.duckdb
GRANT SELECT ON analytics.orders TO PUBLIC;                               -- every store user
REVOKE GRANT OPTION FOR SELECT ON CATALOG my FROM loader;
REVOKE INSERT ON analytics.orders FROM loader;                            -- CASCADE by default
-- RESTRICT fails if other grants depend on this one:
REVOKE SELECT ON analytics.orders FROM PUBLIC RESTRICT;
```

`WITH GRANT OPTION` lets the grantee pass a privilege on; `WITH ADMIN OPTION` lets a role
member grant the role. A revoke cascades to the grants made through it unless you say
`RESTRICT`. A grant on a schema or catalog covers objects created there later.

### Nested schemas

DuckDB 2.0 nests schemas: `CREATE SCHEMA analytics.archive` makes `archive` inside `analytics`,
and its objects are reached only by their whole path, `analytics.archive.orders_2024`. A grant
records that whole path. A grant on `analytics` covers every schema nested in it; a grant on
`analytics.archive` covers `analytics.archive.*` and nothing alike: not `reports.archive`, not a
top-level schema named `"analytics.archive"` (quoted, with the dot in its name), not
`analytics_eu`. Names in `GRANT`, `REVOKE`, the policy statements and `ALTER ... OWNER TO` are read
the way DuckDB binds them in a query: the first part is a catalog when one by that name is
attached, else the whole qualifier is a schema path of the session's catalog. A name that reads
both ways is refused rather than guessed; write the nested one with its catalog
(`my.analytics.archive.orders_2024`).

```sql test profile=rbac
CREATE SCHEMA analytics.archive;
CREATE TABLE analytics.archive.orders_2024 AS SELECT * FROM analytics.orders;
GRANT CREATE SCHEMA ON SCHEMA analytics TO analyst;      -- schemas nested in analytics
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='joe-secret' hardcharger --host localhost --tls=false --username joe --csv \
    --command "SELECT count(*) AS n FROM analytics.archive.orders_2024"
n
2
$ HARDCHARGER_PASSWORD='joe-secret' hardcharger --host localhost --tls=false --username joe --csv \
    --command "CREATE SCHEMA analytics.joes"
OK
$ HARDCHARGER_PASSWORD='joe-secret' hardcharger --host localhost --tls=false --username joe --csv \
    --command "CREATE SCHEMA joes" 2>&1 | grep -o "no CREATE SCHEMA privilege on catalog my"
no CREATE SCHEMA privilege on catalog my
```

A child schema is created with `CREATE SCHEMA` on its parent (granted `ON SCHEMA`, `ON CATALOG`, or
by owning the parent), and its creator owns it: `joe` may now create and drop schemas inside
`analytics.joes` too. `DROP SCHEMA` of a child needs the same as any schema's (owning it, owning its
parent, or `DROP SCHEMA` on it or above it), and `DROP SCHEMA ... CASCADE` needs that for every
schema nested below it.

DuckDB's own listings (`duckdb_schemas()`, `duckdb_tables()`, `information_schema`) show a nested
schema by its leaf name, with `parent_schema` telling two `archive`s apart; Hardcharger lists
nested objects to whoever may see them. `hardcharger_grants()`, `SHOW GRANTS` and the drivers'
metadata calls name a nested schema by its path, `analytics.archive`, writing a part quoted when it
contains a dot or a double quote, so that `"analytics.archive"` (a top-level schema of that name)
reads differently.

### System privileges

Reaching outside the database needs a system privilege, granted to a role with no object `ON`
clause:

| System privilege | Opens |
|---|---|
| `READ FILESYSTEM` | reading the server's own files: `read_csv`, `read_parquet`, `glob`, `FROM 'file'`, `COPY … FROM` |
| `WRITE FILESYSTEM` | `COPY … TO` a file on the server |
| `READ OBJECT STORAGE` | reading `s3://`, `gs://`, `r2://`, `az://`, `abfss://` |
| `WRITE OBJECT STORAGE` | `COPY … TO` object storage |
| `READ HTTP` | reading `http://`, `https://`, `hf://` |
| `WRITE HTTP` | `COPY … TO` an `http(s)://` URL |
| `MANAGE CATALOGS` | `ATTACH`, `DETACH` |
| `MANAGE EXTENSIONS` | `INSTALL`, `LOAD`, `UPDATE EXTENSIONS`, extension repositories |
| `MANAGE SECRETS` | `CREATE`/`DROP SECRET`, `duckdb_secrets()` |
| `MANAGE CONFIG` | `SET GLOBAL`, instance-wide settings, reading settings that hold credentials |
| `EXPORT DATABASE`, `IMPORT DATABASE` | those statements |
| `CHECKPOINT` | `CHECKPOINT`, `FORCE CHECKPOINT` |

```sql test profile=rbac
CREATE ROLE ingest;
GRANT READ FILESYSTEM TO ingest;
GRANT ingest TO joe;
```

Each kind of storage has its own privilege, so a role that reads the server's files reaches no
bucket and no URL. `joe` can read files now, but not the web:

```console test profile=rbac exit=1
$ HARDCHARGER_PASSWORD='joe-secret' hardcharger --host localhost --tls=false --username joe \
    --command "SELECT * FROM read_csv('https://example.com/orders.csv')"
Error: Hardcharger blocked read_csv() of 'https://example.com/orders.csv', which needs the READ HTTP system privilege, everywhere or on a location that covers it. User joe does not hold it (see SHOW GRANTS)
```

A few things no privilege opens, such as `query()` with SQL text built at run time; those stay
with the administrator.

#### Storage privileges on locations

The six storage privileges can also be granted on a location: a bucket and prefix, a host and
path, or an absolute directory or file on the server. A location covers itself and everything
below it, and nothing else:

```sql test profile=rbac
CREATE ROLE landing;
GRANT READ OBJECT STORAGE ON LOCATION 's3://acme-landing/orders/' TO landing;
GRANT WRITE OBJECT STORAGE ON LOCATION 's3://acme-exports/finance/' TO landing;
GRANT READ HTTP ON LOCATION 'https://data.example.com/public/' TO landing;
GRANT READ FILESYSTEM ON LOCATION '/srv/landing/' TO landing;
REVOKE READ HTTP ON LOCATION 'https://data.example.com/public/' FROM landing;
```

`SHOW GRANTS` and `hardcharger_grants()` list these with object type `LOCATION` and the location
as Hardcharger stores it (see below). `WITH ADMIN OPTION` on a location lets its holder grant that
location or any location below it.

Paths are compared as DuckDB opens them, not as they are spelled:

- Scheme aliases are one scheme (`s3a://` and `s3n://` are `s3://`, `gcs://` is `gs://`, `azure://`
  is `az://`), bucket, container and host names are compared in lower case, and a trailing `/` makes
  no difference. `s3://acme-landing/orders` covers `s3://acme-landing/orders/2026/10.csv`, not
  `s3://acme-landing/orders-old/`.
- A local path is compared with symlinks resolved, so a symlink can't lead out of a location:
  not the path a statement names, and not any file it opens, lists or matches with a glob
  (a match that leads out is left out of the listing).
- A glob is covered when its fixed part is: `s3://acme-landing/orders/*/*.csv` is,
  `s3://acme-landing/*/x.csv` isn't.
- A remote path that could name one object two ways is refused instead of compared: `.` or `..`
  segments, `//`, backslashes, user information in the host, percent-escapes in object storage
  (on the web, escaped `.`, `/` and `\`), and `?` or `#` in object storage, where DuckDB reads
  query parameters as S3 settings (the endpoint and credentials among them). A query string on an
  `https://` URL is fine. A scheme Hardcharger doesn't know is refused.
- In 2.9.0+, a direct string bind parameter such as `read_csv($1)` is checked against the
  user's storage grants before DuckDB binds the statement. Positional and named JSON string
  parameters are supported. Prepared statements recheck the supplied path and current grants
  on every execution, including after a grant is revoked.
- A path computed by an expression (`read_csv('s3://bucket/' || name)`) or a parameter whose
  path cannot be resolved before binding is refused unless the user holds the privilege for
  every kind of storage everywhere. Use a literal path or a direct string bind parameter.

#### DuckLake storage is DuckLake's

No user reads, writes, lists or globs an attached DuckLake catalog's data path directly, whatever
storage privileges they hold. Statements on the catalog's tables still read and write there under
the tables' grants, because DuckLake does that itself; the administrator may still look. A file
written into a lake's storage could be registered as a table's rows, and a listing shows another
catalog's files, so `COPY … TO` a lake's path, `read_parquet` of a lake's files and `glob` over
them are refused, and so is a glob, or a `COPY … TO` with `PARTITION_BY`, aimed above a lake's path,
or a symlink that leads into one.

#### Upgrading from 2.1

Before 2.2, `READ FILESYSTEM` also covered object storage and URLs, and `WRITE FILESYSTEM` the same
for writes. On its first start, 2.2 gives every role that holds `READ FILESYSTEM` everywhere
`READ OBJECT STORAGE` and `READ HTTP` everywhere too (and `WRITE FILESYSTEM`, the two `WRITE` ones),
with the same admin option and grantor, so nothing that worked stops working. Revoke what a role
doesn't need; a revoke is not undone at the next start. A 2.1 server sharing the store doesn't see
the new privileges or any location grant, so it refuses what they allow.

## Ownership and views

The user who creates an object owns it and can grant on it. Move ownership with:

```sql test profile=rbac
ALTER TABLE analytics.orders OWNER TO ROLE loader;
```

A view reads with its **owner's** rights, so you can publish a filtered or aggregated view of a
table without granting the table:

```sql test profile=rbac
CREATE SCHEMA published;
CREATE VIEW published.revenue_by_region AS
  SELECT region, sum(amount) AS revenue FROM analytics.orders GROUP BY region;
CREATE ROLE viewer;
GRANT SELECT ON published.revenue_by_region TO viewer;
CREATE USER vic WITH PASSWORD 'vic-secret';
GRANT viewer TO vic;
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "SELECT * FROM published.revenue_by_region ORDER BY region"
region,revenue
EU,120.0
US,80.0
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "SELECT * FROM analytics.orders" > /dev/null 2>&1 || echo "refused"
refused
```

Creating a view takes more than `CREATE VIEW` on its schema: the creator must be able to `SELECT`
everything the view's query reads, each table, view and column, as their own `SELECT` of the query
would. Otherwise a view would let its owner see the shape of a table they hold nothing on.

```sql test profile=rbac
CREATE ROLE view_maker;
GRANT CREATE VIEW ON SCHEMA published TO view_maker;
GRANT view_maker TO vic;
```

```console test profile=rbac exit=1
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "CREATE VIEW published.all_orders AS SELECT * FROM analytics.orders"
Error: Permission Error: Hardcharger blocked this statement: user vic may create a view only over what it can SELECT itself, and the query of view my.published.all_orders reads more: user vic has no SELECT privilege on table my.analytics.orders. Access control on this server lets user vic do only what their roles are granted (see SHOW GRANTS)
```

Once created, a view still reads with its owner's rights, so one granted to others keeps working,
and revoking the owner's access closes it.

### Renaming, dropping and recreating objects (v2.11.0+)

A table or view rename carries its object grants, ownership and policy bindings to the new
name. Dropping an object removes its access-control records. `DROP SCHEMA ... CASCADE`
also removes the records for nested schemas and their objects. These rules apply to
administrator and prepared statements too.
In an explicit transaction, drop cleanup waits for commit; rollback preserves the existing
records. Cleanup deletes the rows from the configured PostgreSQL or DuckDB store.

Here, `vic` keeps access after the rename through the `viewer` role created above:

```sql test profile=rbac
CREATE SCHEMA lifecycle;
CREATE ROLE lifecycle_owner;
CREATE TABLE lifecycle.report AS SELECT 42 AS answer;
ALTER TABLE lifecycle.report OWNER TO ROLE lifecycle_owner;
GRANT SELECT ON lifecycle.report TO viewer;
ALTER TABLE lifecycle.report RENAME TO renamed_report;
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "SELECT * FROM lifecycle.renamed_report"
answer
42
```

A new object at an old name does not inherit the old object's grants. Broader grants on its
schema or catalog still apply. Creating a genuinely new object first clears stale records
for its name; if the access-control store cannot be reached for that cleanup, creation
fails. `CREATE ... IF NOT EXISTS` against an existing object retains its owner and grants.
If a cleanup write fails after a drop, the server logs the failure; reusing that name still
requires successful cleanup first.

```sql test profile=rbac
DROP TABLE lifecycle.renamed_report;
CREATE TABLE lifecycle.renamed_report AS SELECT 99 AS answer;
ALTER TABLE lifecycle.renamed_report OWNER TO ROLE lifecycle_owner;
```

```python test profile=rbac
from adbc_driver_hardcharger import dbapi as hardcharger

with hardcharger.connect(uri="hardcharger://localhost?tls=false", username="vic", password="vic-secret") as conn:
    with conn.cursor() as cur:
        try:
            cur.execute(operation="SELECT * FROM lifecycle.renamed_report")
        except hardcharger.ProgrammingError as error:
            assert "permission_denied" in str(error)
            print("The recreated table needs a new grant.")
        else:
            raise AssertionError("An old grant survived the drop.")
```

```text output
The recreated table needs a new grant.
```

Dropping the schema also removes the table's ownership, so the role can be dropped:

```sql test profile=rbac
DROP SCHEMA lifecycle CASCADE;
DROP ROLE lifecycle_owner;
```

For ownership records left by older versions, `DROP USER` and `DROP ROLE` check whether each
owned object still exists. A confirmed missing object in an attached catalog no longer
blocks the operation. A detached catalog or a failed lookup is treated as unknown: attach
the catalog and retry, or transfer ownership of existing objects before dropping the
principal. You do not need to create a replacement table to remove a stale ownership record.

### Macros

`CREATE MACRO` on a schema (or its catalog, or owning the schema) lets a role create scalar and
table macros there; `DROP MACRO` lets it drop them, and replacing one (`CREATE OR REPLACE`) needs
both. Anyone may call a macro: DuckDB expands it into the statement that calls it, so what its body
reads is checked as part of that statement, with the caller's rights. A macro over a table only
some users may read works for them and is refused to the rest.

```sql test profile=rbac
GRANT CREATE MACRO, DROP MACRO ON SCHEMA published TO view_maker;
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "CREATE MACRO published.cents(amount) AS CAST(amount * 100 AS INTEGER)"
OK
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "SELECT published.cents(1.25) AS cents"
cents
125
```

A user's macro must not change what anyone else's SQL computes, so Hardcharger refuses, to
everyone but the administrator:

- **temporary macros**: a session's macro is found before every other function, also inside a
  view that reads with its owner's rights;
- **a built-in function's name**, or that of a function an extension autoloads (`lower`,
  `read_csv`, `st_area`): DuckDB would find the macro instead, in every query and view;
- **replacing, or standing in for, a function that a view, a trigger, a row or masking policy,
  or a macro one of them uses calls**: the view reads with its owner's rights, a trigger's body
  with its owner's, and a row policy could be made true;
- **a body that calls what its creator may not**: `query()`, `query_table()`, remote queries, and
  files, URLs or object storage beyond the creator's system privileges. (DuckDB binds the body
  where the macro is called, and binding a table function already reads.)

```console test profile=rbac exit=1
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "CREATE MACRO published.lower(x) AS 'mine'"
Error: Permission Error: Hardcharger blocked this statement: a macro named lower would replace the built-in function lower wherever it is called, in queries and views alike; give the macro a name of its own. …
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "CREATE TEMP MACRO mine(x) AS x"
Error: Permission Error: Hardcharger blocked this statement: creating temporary macros needs an administrator: …
```

### Types

`CREATE TYPE` on a schema (or its catalog, or owning the schema) lets a role create enums, structs
and type aliases there; `DROP TYPE` lets it drop them, and replacing one (`CREATE OR REPLACE`) needs
both. Anyone may use a type. An enum made from a query (`CREATE TYPE t AS ENUM (SELECT ...)`) reads
with its creator's rights.

```sql test profile=rbac
GRANT CREATE TYPE, DROP TYPE ON SCHEMA published TO view_maker;
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "CREATE TYPE published.priority AS ENUM ('low', 'high')"
OK
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "SELECT typeof('high'::published.priority) AS t"
t
"ENUM('low', 'high')"
```

A type is found by name where SQL is bound (a view's query, a macro's or trigger's body, a policy, a
column default or `CHECK` constraint), so a user's type could stand in for one of those, and dropping
or replacing a type they name would change what they compute. Hardcharger refuses, to everyone but
the administrator:

- **temporary types**: a session's type is found before every other type, also inside a view that
  reads with its owner's rights;
- **a built-in type's name**, or that of a type an extension provides (`integer`, `json`): DuckDB
  finds a schema's type before the built-in one;
- **a name that a view, a macro, a trigger, a row or masking policy, or a column default or check
  constraint resolves to another type**, and dropping or replacing such a type.

A table's columns pin nothing: DuckDB copies the type into the column at `CREATE TABLE`, so dropping
or replacing the type changes nothing there. `duckdb_types()` lists a user's own schemas' types and
the built-in ones.

```console test profile=rbac exit=1
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "CREATE TYPE published.integer AS VARCHAR"
Error: Permission Error: Hardcharger blocked this statement: a type named integer would replace the built-in type integer wherever it is named, in queries and views alike; give the type a name of its own. …
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "CREATE TEMP TYPE mine AS INTEGER"
Error: Permission Error: Hardcharger blocked this statement: creating temporary types needs an administrator: …
```

### Triggers

A trigger's body runs inside every write of its table, so creating one takes ownership of the
table and `CREATE TRIGGER` on its schema (or its catalog, or owning the schema). The creator owns
the trigger: only the owner, or a role granted `DROP TRIGGER` on the schema, drops or replaces it.

Whose rights a body runs with depends on who made the trigger:

- **A user's trigger runs with its owner's rights**, whoever writes the table (definer rights). The
  body is checked, and row and masking policies applied, as if the owner ran it: a writer who may
  only `INSERT` into the table still fires a trigger that writes the owner's log table, and an
  administrator's write lends the body no administrator rights. A body that does what its owner may
  not do refuses the write, naming the trigger and its owner.
- **An administrator's trigger runs with the writer's rights**, as DuckDB runs it: a user who
  inserts into such a table needs the rights for everything the trigger does, and is refused
  otherwise.

What a body calls is checked when the trigger is created, as a macro's body is: no `query()`,
`query_table()` or remote queries, and files, URLs or object storage only within the creator's
storage privileges. The functions a body calls are pinned like the ones a view calls: no user's
macro can take their place. `duckdb_triggers()` lists the triggers of the tables a user may access.

```sql test profile=rbac
GRANT CREATE TABLE, CREATE TRIGGER ON SCHEMA published TO view_maker;
CREATE USER wes WITH PASSWORD 'wes-secret';
GRANT viewer TO wes;
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "CREATE TABLE published.ticket_notes (ticket_id BIGINT, note VARCHAR)"
OK
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "CREATE TABLE published.note_log (what VARCHAR)"
OK
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "CREATE TRIGGER log_notes AFTER INSERT ON published.ticket_notes FOR EACH STATEMENT INSERT INTO published.note_log VALUES ('note added')"
OK
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "GRANT INSERT ON published.ticket_notes TO viewer"
result
Granted INSERT on my.published.ticket_notes to viewer
```

wes may write `ticket_notes` and nothing else in `published`; the trigger's body writes `note_log`
with vic's rights:

```console test profile=rbac
$ HARDCHARGER_PASSWORD='wes-secret' hardcharger --host localhost --tls=false --username wes --csv \
    --command "INSERT INTO published.ticket_notes VALUES (1, 'called back')"
OK, 1 row affected
$ HARDCHARGER_PASSWORD='wes-secret' hardcharger --host localhost --tls=false --username wes --csv \
    --command "INSERT INTO published.note_log VALUES ('by wes')" 2>&1 | grep -o "has no INSERT privilege on table [a-z_.]*note_log"
has no INSERT privilege on table my.published.note_log
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
```

### Sequences

`nextval()` and `currval()` need `USAGE` on the sequence, granted `ON SEQUENCE`, `ON SCHEMA` or `ON
CATALOG` (or owning its schema); `setval()` resets a sequence, which dropping and recreating it
would do too, so it needs `DROP SEQUENCE` on its schema. `CREATE SEQUENCE` and `DROP SEQUENCE` are
granted on a schema or catalog. A table's own column default is part of writing the table: `INSERT`
on it covers the sequence its default advances, so an ordinary insert needs no grant on the
sequence, while writing such a default (`CREATE TABLE`, `ALTER TABLE ... SET DEFAULT`) needs `USAGE`
on it. Inside a view the view owner's `USAGE` counts; inside a macro, the caller's.

```sql test profile=rbac
CREATE SEQUENCE published.ticket_ids;
CREATE TABLE published.tickets (id BIGINT DEFAULT nextval('published.ticket_ids'), title VARCHAR);
GRANT INSERT, SELECT ON published.tickets TO viewer;
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "INSERT INTO published.tickets (title) VALUES ('first')"
OK, 1 row affected
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "SELECT nextval('published.ticket_ids') AS n" 2>&1 | grep -o "has no USAGE privilege on sequence [a-z_.]*ticket_ids"
has no USAGE privilege on sequence my.published.ticket_ids
```

`duckdb_sequences()` and the views over it list only the sequences a user may use or drop.

### Maintenance

`MAINTAIN` lets a role run `ANALYZE` and `VACUUM` of a table and nothing else: no `SELECT`, no
writes. It is granted on a table, a schema or a catalog, and a table's owner holds it. `ANALYZE` or
`VACUUM` without a table stays the administrator's, since it would touch tables the user can't see.

```sql test profile=rbac
GRANT MAINTAIN ON published.tickets TO viewer;
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "ANALYZE published.tickets"
OK
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "ANALYZE" 2>&1 | grep -o "ANALYZE or VACUUM of every table needs an administrator"
ANALYZE or VACUUM of every table needs an administrator
```

### Comments

`COMMENT ON` follows the right to change the object: a table, a column of one, or an index on one
needs `ALTER TABLE` on the table (its owner holds it); a view or a column of one, `ALTER VIEW`; a
sequence, `DROP SEQUENCE` on its schema; a macro, `DROP MACRO` on its schema; a type, `DROP TYPE` on
its schema.

```sql test profile=rbac
GRANT ALTER TABLE ON SCHEMA published TO view_maker;
```

```console test profile=rbac
    --command "COMMENT ON TABLE published.tickets IS 'support tickets'"
OK
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \

may not comment on table my.analytics.orders
```

### Table functions

Under access control, a table function that reads no table and no file (`range()`, `generate_series()`,
the `duckdb_*()` listings) is every user's, one that reads files (`read_csv()`, `read_parquet()`,
`read_text()`, ...) goes through the [system privileges](#system-privileges) for storage, and any
other, an extension's say, is the administrator's. `EXECUTE` opens one such function to a role:

```sql test profile=rbac
GRANT EXECUTE ON TABLE FUNCTION pg_timezone_names TO viewer;
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "SELECT count(*) > 100 AS many FROM pg_timezone_names()"
many
true
$ HARDCHARGER_PASSWORD='joe-secret' hardcharger --host localhost --tls=false --username joe --csv \
    --command "SELECT count(*) FROM pg_timezone_names()" 2>&1 | grep -o "or to a role granted EXECUTE ON TABLE FUNCTION pg_timezone_names"
or to a role granted EXECUTE ON TABLE FUNCTION pg_timezone_names
```

A function that reads files takes its paths as arguments, and the grant says which: `PATH ARGUMENT n`
(the n-th positional argument, 1 the first; `PATH ARGUMENTS 1, 2` for several) or `PATH PARAMETER name`
(a named one). The value there goes through the storage privileges as every `read_csv()` path does,
as written, before DuckDB opens the file, and again as bound; a computed path is refused. The
operator who loads an extension decides what its functions read, so the declaration is theirs to
get right: an undeclared path argument is read unchecked. `sqlite_scan(path, table)` reads the
SQLite file its first argument names:

```sql test profile=rbac
ATTACH 'tickets.sqlite' AS lite (TYPE sqlite);
CREATE TABLE lite.open_tickets AS SELECT 1 AS id, 'first' AS title;
DETACH lite;
GRANT EXECUTE ON TABLE FUNCTION sqlite_scan (PATH ARGUMENT 1) TO viewer;
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "SELECT * FROM sqlite_scan('tickets.sqlite', 'open_tickets')" 2>&1 | grep -o "which needs the READ FILESYSTEM system privilege"
which needs the READ FILESYSTEM system privilege
```

```sql test profile=rbac
GRANT READ FILESYSTEM TO viewer;
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "SELECT * FROM sqlite_scan('tickets.sqlite', 'open_tickets')"
id,title
1,first
```

A table macro an administrator wraps around the function (`CREATE MACRO lite(p) AS TABLE SELECT *
FROM sqlite_scan(p, 'open_tickets')`) works for the grantee the same way: DuckDB expands it, and
the function and its paths are checked as above. `EXECUTE` is never part of `GRANT ALL`, and a
grant made again replaces the function's path declaration. It can't be granted on a function every
user may call already, on one the storage privileges check, or on one that stays the
administrator's: the server's own `hardcharger_*()`, `query()` and `query_table()`,
`duckdb_secrets()`, `checkpoint()`, and the engine's internals (`arrow_scan()`, the logging and
profiling functions, `duckdb_logs()`, `pragma_storage_info()`, ...). `hardcharger_grants()`,
`hardcharger_effective_privileges()` and `SHOW GRANTS` list it as `EXECUTE` on a `TABLE FUNCTION`,
with the declared path arguments where `SELECT` lists columns.

## What users can see

From v2.11.0, ordinary RBAC users and catalog-restricted sessions do not receive DuckDB's
catalog spelling suggestions or candidate-name lists in errors. A misspelled name cannot
use those hints to reveal hidden table, schema or column names. Unrestricted administrators
still receive the engine's diagnostic suggestions.

```python test profile=rbac
from adbc_driver_hardcharger import dbapi as hardcharger

with hardcharger.connect(uri="hardcharger://localhost?tls=false", username="vic", password="vic-secret") as conn:
    with conn.cursor() as cur:
        try:
            cur.execute(operation="SELECT * FROM analytics.ordres")
        except hardcharger.ProgrammingError as error:
            message = str(error)
            assert "does not exist" in message
            assert "Did you mean" not in message
            assert "Candidate tables:" not in message
            print("Missing-object error without catalog suggestions.")
        else:
            raise AssertionError("The misspelled table unexpectedly exists.")
```

```text output
Missing-object error without catalog suggestions.
```

Metadata follows privileges, table by table. A user sees a table or view only when they hold a
privilege on it (`SELECT` on it or on any of its columns, `INSERT`, `UPDATE` or `DELETE`; owning it
holds them all), a column only when they may read it, and a schema only when they hold a grant on
or in it or own something there. That covers the drivers' metadata calls (ADBC `GetObjects`, JDBC
`DatabaseMetaData`) and SQL's own listings: `information_schema`, `duckdb_tables()`,
`duckdb_columns()` and the other `duckdb_*()` functions, `SHOW TABLES`, `SHOW ALL TABLES`,
`pragma_table_info()`. DuckDB's own views (catalog `system`) and the session's temporary objects
stay listed. `vic` sees the view he may read and the table his role may write:

```console test profile=rbac
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "SELECT table_schema, table_name FROM information_schema.tables WHERE table_catalog = 'my' ORDER BY table_name"
table_schema,table_name
published,note_log
published,revenue_by_region
published,ticket_notes
published,tickets
```

`DESCRIBE` (and `SHOW <table>`) of a table the user holds no privilege on is refused, and so is
`DESCRIBE` of a table they may read only some columns of, since it would show them all;
`pragma_table_info()` lists the columns they may read:

```console test profile=rbac exit=1
$ HARDCHARGER_PASSWORD='vic-secret' hardcharger --host localhost --tls=false --username vic --csv \
    --command "DESCRIBE analytics.orders"
Error: Hardcharger blocked this statement: user vic holds no privilege on table my.analytics.orders, so it cannot describe it
$ HARDCHARGER_PASSWORD='joe-secret' hardcharger --host localhost --tls=false --username joe --csv \
    --command "DESCRIBE main.customers"
Error: Hardcharger blocked this statement: user joe may read only some columns of table my.main.customers, and DESCRIBE shows them all; pragma_table_info('my.main.customers') lists the ones it may read
```

```console test profile=rbac
$ HARDCHARGER_PASSWORD='joe-secret' hardcharger --host localhost --tls=false --username joe --csv \
    --command "SELECT name FROM pragma_table_info('main.customers')"
name
id
email
```

Where a database lives is the administrator's to see: `duckdb_databases().path` is `NULL` for
everyone else, because an attached catalog's path can be its connection string, password included.

A grant or revoke applies to the next listing, prepared ones included. Scoped tokens, `SET ROLE`,
tenants and [catalog access rules](/guides/catalog-access-rules/) narrow what is listed the same
way they narrow what can be read.

## Seeing grants

```console test profile=rbac
$ HARDCHARGER_PASSWORD='change-me' hardcharger --host localhost --tls=false --username hardcharger --csv \
    --command "SHOW GRANTS FOR ROLE analyst"
privilege,object_type,object,columns,granted_to,grantee_type,grant_option,granted_by
…
```

`SHOW GRANTS` alone shows your own. Its columns are `privilege, object_type, object, columns,
granted_to, grantee_type, grant_option, granted_by`. Store users may look at themselves and the
roles they hold.

The same, as tables to query: `hardcharger_grants()`, `hardcharger_role_members()`,
`hardcharger_roles()`, `hardcharger_users()`, `hardcharger_policies()` and
`hardcharger_effective_privileges([user_name])` ([SQL reference](/reference/sql/#functions)).
`hardcharger_effective_privileges()` lists what a user may do and through which role (the schema
`joe` created in [Nested schemas](#nested-schemas) is his, as `OWNERSHIP`):

```console test profile=rbac
$ HARDCHARGER_PASSWORD='joe-secret' hardcharger --host localhost --tls=false --username joe --csv \
    --command "SELECT privilege, object_type, schema_name, object_name, column_name, via FROM hardcharger_effective_privileges() ORDER BY ALL"
privilege,object_type,schema_name,object_name,column_name,via
CREATE SCHEMA,SCHEMA,analytics,NULL,NULL,analyst
OWNERSHIP,SCHEMA,analytics.joes,NULL,NULL,OWNER
READ FILESYSTEM,SYSTEM,NULL,NULL,NULL,ingest
SELECT,SCHEMA,analytics,NULL,NULL,analyst
SELECT,TABLE,main,customers,email,analyst
SELECT,TABLE,main,customers,id,analyst
```

They read the server's copy of the store, so they cost no store query. The administrator sees
everything; a store user sees its own grants, memberships, roles and user row, and the policies
on tables it can see; a tenant admin also its own tenant's. The SQL standard's views
(`table_privileges`, `column_privileges`, `role_table_grants`, `applicable_roles`,
`enabled_roles`) are in `_hardcharger_system.hardcharger_information_schema`, with the standard's
columns.

## Managing users

```sql test profile=rbac
CREATE USER ann WITH PASSWORD 'ann-secret';
ALTER USER joe WITH PASSWORD 'n3w-secret';   -- ends joe's tokens and sessions at once
ALTER USER joe DISABLE;                      -- and ENABLE
ALTER USER joe PASSWORD NULL;                -- token sign-in only (SSO, scoped tokens)
ALTER USER ann SET ATTRIBUTE region = 'EU';  -- for row policies: session_attribute('region')
DROP USER IF EXISTS ann;
```

Dropping or disabling a user, changing their password, or revoking a role takes effect on every
replica within about a second, including in sessions that are open: a revoke can stop a
statement that is running. The user's tokens stop working at once (`401 invalid_token`, with a
[`reason`](/reference/errors/#invalid_token-reasons) that says why), and once they sign in again,
their old sessions answer `401 session_ended` with a
[`reason`](/reference/errors/#session_ended-reasons): `principal_dropped` (dropped or disabled) or
`credentials_changed` (a new password, or anything else access control revoked).

## Users who sign in with a certificate

With [certificate sign-in](/guides/tls/#signing-in-with-the-certificate) on, a client certificate
signs in as the store user its identity names (by default its e-mail SAN; ASCII case doesn't
matter, except in URI identities such as SPIFFE IDs). Such a user needs no password, and roles
decide what it may do, as for any user. The administrator signs in with a password here over a
plain client certificate, since this server requires one on every connection:

```console test profile=rbac_mtls
$ HARDCHARGER_PASSWORD='change-me' hardcharger --host localhost --username hardcharger --tls --tls-roots ca.crt \
    --mtls-cert client.crt --mtls-key client.key --csv --command 'CREATE ROLE sales_reader;
      CREATE TABLE sales AS SELECT 42 AS amount;
      GRANT SELECT ON sales TO sales_reader;
      CREATE USER "joe@example.com";
      GRANT sales_reader TO "joe@example.com"'
result
Role sales_reader created
OK, 1 row affected
result
Granted SELECT on my.main.sales to sales_reader
result
User joe@example.com created
result
Granted sales_reader to joe@example.com
```

`joe.crt` carries `email:joe@example.com`. Joe signs in with it alone:

```console test profile=rbac_mtls
$ hardcharger --host localhost --tls --tls-roots ca.crt --auth-type mtls \
    --mtls-cert joe.crt --mtls-key joe.key --csv --command "SELECT HARDCHARGER_USER() AS who, amount FROM sales"
who,amount
joe@example.com,42
```

A certificate whose identity is no user (or a disabled one) is refused with
`unknown_certificate_identity`.

## Users and roles from init SQL

In **v2.4.0+**, the server's [init SQL](/guides/configuration/) can create users and roles and
grant privileges. These statements run as the administrator, in order with the DuckDB statements
around them, so a grant can name a table the init SQL has just created. The init SQL runs at every
start and on every replica, so write it to run again harmlessly:

```sql test file=init.sql
CREATE SCHEMA IF NOT EXISTS sales;
CREATE TABLE IF NOT EXISTS sales.orders AS
  SELECT * FROM (VALUES (1, 'EU', 120.0), (2, 'US', 80.0)) t(id, region, amount);
CREATE ROLE IF NOT EXISTS reader;
GRANT SELECT ON SCHEMA sales TO reader;
CREATE USER IF NOT EXISTS ann WITH PASSWORD 'ann-secret';
GRANT reader TO ann;
```

```bash test server=self background
HARDCHARGER_ADMIN_PASSWORD='change-me' HARDCHARGER_RBAC_STORE_URI='duckdb:startup-rbac.duckdb' \
  hardcharger-server --database shop.duckdb --health-port 31338 --init-sql-commands-file init.sql
```

```console test server=none
$ HARDCHARGER_PASSWORD='ann-secret' hardcharger --host localhost --tls=false --username ann --csv \
    --command "SELECT sum(amount) AS total FROM sales.orders"
total
200.0
```

Without `rbac_store_uri`, an access-control statement in the init SQL stops the server before
any of the init SQL runs, with the error a session gets (`access control is not enabled on this
server`). A password in the init SQL is as sensitive as the file's secrets: the server never logs
it, and the [sensitive path guard](/concepts/security-model/#guards-that-apply-to-everyone) keeps
the file out of reach of SQL, but keep it readable only by the server's user.

## Checking a credential without the server

`hardcharger-server --verify-credentials` decides a credential the way `/chargewire/v1/auth/token`
would, with the server's own configuration (the administrator, the store, the token keys, the
secret key) and nothing written anywhere: the store is opened read-only, never claimed, created
or upgraded, and a user that `token_auto_provision_users` would create is reported, not created.
It is for a control plane that must know whether a credential is good before it starts a stopped
server, without keeping a copy of the store's credentials.

It reads one JSON object on stdin, exactly what a client sends to the token endpoint (a password
grant, a scoped token as the password of user `token`, or a `token_exchange` grant), prints one
JSON line on stdout, and logs to stderr. Here a server with its store in a DuckDB file creates a
user:

```sql test profile=rbac_duckdb stop
CREATE USER ops WITH PASSWORD 'ops-secret';
```

Then, with that server stopped, the check runs with the same configuration:

```console test server=self
$ export HARDCHARGER_ADMIN_PASSWORD=change-me HARDCHARGER_RBAC_STORE_URI=duckdb:rbac.duckdb
$ echo '{"grant_type": "password", "username": "ops", "password": "ops-secret"}' | hardcharger-server --verify-credentials 2>/dev/null
{"verified":true,"user":"ops","role":"user","method":"password","would_provision":false}
$ echo '{"grant_type": "password", "username": "ops", "password": "wrong"}' | hardcharger-server --verify-credentials 2>/dev/null; echo "exit $?"
{"verified":false,"reason":"invalid_credentials","message":"the user name or password is not correct"}
exit 1
```

The exit code is 0 for a credential that signs in, 1 for one that does not (`reason` is the error
code the client would get, or a token's reason such as `token_expired`), 2 for bad input, and 3 when
nothing could be decided: the store is unreachable (`store_unavailable`), has no schema yet
(`store_uninitialized`), belongs to another cluster (`store_belongs_to_another_cluster`), or the
configuration is wrong. A DuckDB file store can be checked only while no server has it open
(DuckDB's file lock); a PostgreSQL store can be checked at any time. A scoped token is bound to the
process that issued it unless `allow_cross_instance_tokens` is on, so without it, and without a
configured `secret_key`, no earlier token verifies, which is also what the server would say after a
restart. The credential never appears in the output or the log.

## Active roles

A user's roles are all active by default. `SET ROLE analyst` narrows a session to one role,
`SET ROLE ALL` restores them, `SET ROLE NONE` drops to `PUBLIC`'s grants. Row policies can test
roles with `is_role_active('hr')`.
