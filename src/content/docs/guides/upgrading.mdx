import { Aside, Steps } from '@astrojs/starlight/components';

Hardcharger follows [semantic versioning](https://semver.org). Before 1.0, a minor version
(`0.3` to `0.4`) may change options or behavior; the [release notes](/reference/release-notes/)
say what, under **Changed**. Patch versions only fix things.

<Steps>

1. **Read the release notes** for every version between yours and the new one. Look for renamed
   options (an unknown option stops the server at startup, so you'll know at once) and changed
   defaults.

2. **Check the database file format.** DuckDB 2.0 reads files written by DuckDB 1.x. An existing
   plain DuckDB database retains its format unless you request an upgrade.
   **v2.1.0+ removes Hardcharger’s DuckLake metadata compatibility patch:** upstream DuckLake
   can upgrade a DuckDB metadata file on writes/checkpoints so older readers cannot reopen
   it. Back up metadata before upgrading. `storage_version` does not override DuckLake’s
   metadata choice. See [extension and metadata compatibility](/guides/extensions/#ducklake-metadata-compatibility).

3. **Upgrade.**

   - Installer: `curl https://install.hardcharger.gizmodata.com | HARDCHARGER_VERSION=0.3.0 sh`
     installs the version next to the others and switches to it. Restart the server.
   - Docker or Kubernetes: change the image tag. Pin versions (`:0.3.0`), not `:latest`, so
     that a restart never upgrades by surprise.
   - Python: `pip install --upgrade hardcharger` downloads the server version the package pins.

4. **Restart gracefully.** On `SIGTERM` the server stops taking new work and lets running
   statements finish ([graceful shutdown](/guides/statement-control/#graceful-shutdown)). With
   several replicas, upgrade one at a time: drivers move to a new session when theirs goes away.

5. **Check** that the new version runs: `SELECT HARDCHARGER_VERSION()`, the health endpoint, and
   your metrics.

</Steps>

## Upgrading to 2.14

### The stores are upgraded in place, and 2.13 can't go back

The first 2.14 server that starts writable on an existing
[access-control store](/guides/access-control/) or
[instrumentation store](/guides/instrumentation-and-audit/) migrates it, then records its new
format: **2.0** for the access-control (RBAC) store, **1.1** for the instrumentation store. Users
keep their passwords, roles and grants, and instrumentation keeps its sessions and query history
under their ids. A store with no recorded format (every store before 2.14) is format 1.0.
`--verify-credentials` opens the store read-only and never upgrades it.

**Hardcharger 2.13 and earlier refuse an access-control store that 2.14 has upgraded**, with
`the access control store's schema is version 2, newer than this server's (1)`: without that,
they would run on it without 2.14's sign-in protections and fail to create users. So:

<Steps>

1. **Back up the access-control store before the first 2.14 server starts** (`pg_dump` of its
   database, or a copy of its DuckDB file while no server has it open), and the instrumentation
   store with it.
2. **Upgrade every replica that shares the store together**: once a 2.14 server has upgraded the
   store, a 2.13 replica can no longer start on it.
3. **To roll back to 2.13, restore the backup**: changes made under 2.14 (users, grants, linked
   sign-ins) are not in it.

</Steps>

The instrumentation store stays readable by 2.13.4, which records correctly on an upgraded one.
An administrator reads its format in the store itself (here the default DuckDB instrumentation
store):

```console test profile=instrumentation
$ HARDCHARGER_PASSWORD='change-me' hardcharger --host localhost --tls=false --username hardcharger --csv \
    --command "SELECT value FROM _hardcharger_instr.main.store_metadata WHERE key = 'schema_version'"
value
1.1
```

The access-control store keeps its format as `schema_version` in `hardcharger_rbac.meta`.

### What changes for existing users and clients

- **New passwords need 12 characters** ([password policy](/guides/access-control/#passwords-v2140)).
  Existing passwords keep working. Init SQL or scripts that create users with shorter passwords
  fail with `the password is too short: it needs at least 12 characters (password_min_length)`.
- **Changing your own password needs the current one**:
  `ALTER USER CURRENT_USER WITH PASSWORD '<new>' REPLACE '<current>'`, for every user but the
  administrator.
- **Failed password sign-ins are limited**: five wrong passwords for one user from one address lock
  that pair for 15 minutes ([failed sign-ins](/guides/access-control/#failed-sign-ins-v2140)).
  A client that retries a wrong password in a loop now gets `429 rate_limited`.
- **Sign-in tokens with `catalog_access` rules no longer use their user's system privileges**
  (`READ FILESYSTEM`, `MANAGE SECRETS`, `CHECKPOINT`, the policy exemptions and the rest), as a
  scoped token's session already didn't. Sign in without the rules for that work
  ([catalog access rules](/guides/catalog-access-rules/)).
- **`current_user`, `session_user` and `user` return the Hardcharger user**, not `duckdb`, and
  `current_role()` the role `SET ROLE` chose. A view that compared them with `'duckdb'` sees the
  user now ([policy functions](/guides/row-policies-and-masking/#policy-functions-and-exemptions)).
- **Reserved names**: a user or role can no longer be named `SYSTEM ADMIN` (one a store already
  has stays an ordinary role, written quoted), and a store user's new macro can no longer be named
  `is_role_active` or `session_attribute`, which are built-in functions now.
- **Progress estimates start after 2 seconds.** The web UI and the CLI show a running statement
  without a percentage for its first `progress_bar_time` (2 seconds); `SET progress_bar_time = 0`
  gives a session estimates from the start.
- **New statement limits**: a FROM clause may join at most 64 tables and a statement 512
  ([`max_joined_tables`](/reference/configuration/#max_joined_tables)), and DuckDB's
  autocomplete functions (`sql_auto_complete()`, `sql_tokenize()`, ...) are refused unless
  [`enable_sql_auto_complete`](/reference/configuration/#enable_sql_auto_complete) is on. The web
  UI's own autocomplete is not affected.
- **SSO accounts are linked to their provider identity** on a first trustworthy sign-in
  ([accounts with both sign-in methods](/guides/sso/#accounts-with-both-sign-in-methods-v2140)). Run 2.14
  on every replica before relying on the links.

## Driver option names (hardcharger-adbc 2.7.0)

From `hardcharger-adbc` 2.7.0 (the Python package `adbc-driver-hardcharger` and the Go module) the
ADBC driver names its options as the
[ADBC driver style guide](https://adbc-drivers.org/building-drivers/style-guide.html) asks: its own
options start with `hardcharger.`, and `adbc.` is left to the options the ADBC specification
defines (`uri`, `username`, `password`, `adbc.connection.readonly`, `adbc.ingest.*`, ...), which
don't change.

- **The old names keep working**, for setting and for reading an option. The first time a process
  uses each one, the driver prints one line to stderr (keys only, never the value):

  ```text
  [hardcharger] option "adbc.chargewire.statement.timeout_seconds" is deprecated; use "hardcharger.query.timeout_seconds"
  ```

- **With both names given, the new one wins.**
- **Python's `connect()` arguments, the `DatabaseOptions`, `ConnectionOptions` and
  `StatementOptions` members, and the Go constants keep their names** and now carry the new keys,
  so code that uses them needs no change.
- **Upgrade the driver before you switch a key**: a 2.6 or older driver refuses the new names.

| Before 2.7.0 | From 2.7.0 |
|---|---|
| `adbc.chargewire.tls.*`, `adbc.chargewire.auth.access_token`, `adbc.chargewire.auth.subject_token`, `adbc.chargewire.retry.max_attempts`, `adbc.chargewire.session.*` | `hardcharger.tls.*`, `hardcharger.auth.access_token`, `hardcharger.auth.subject_token`, `hardcharger.retry.max_attempts`, `hardcharger.session.*` |
| `adbc.chargewire.statement.async`, `.retain_result`, `.timeout_seconds`, `.result_partitions`, `.result_order`, `.id` | `hardcharger.query.async`, `.retain_result`, `.timeout_seconds`, `.result_partitions`, `.result_order`, `.id` |
| `adbc.chargewire.statement.query_tag` (one statement's tag) | `hardcharger.query.tag` |
| `adbc.chargewire.ipc_compression` | `hardcharger.ipc.compression` |
| `adbc.chargewire.resume_timeout`, `adbc.hardcharger.resume_timeout` | `hardcharger.retry.resume_timeout_seconds` |
| `adbc.chargewire.ingest.parts`, `adbc.hardcharger.ingest.parts` | `hardcharger.ingest.parts` |
| `adbc.hardcharger.auth_type` | `hardcharger.auth.type` |
| `adbc.hardcharger.oauth.timeout_seconds`, `.browser`, `.share_sign_in`, `.sign_in_key` | `hardcharger.oauth.timeout_seconds`, `.browser`, `.share_sign_in`, `.sign_in_key` |
| `adbc.hardcharger.session_tag` | `hardcharger.session.tag` |
| `adbc.hardcharger.query_tag` (the session's query tag) | `hardcharger.session.query_tag` |
| `adbc.hardcharger.setting.NAME`, `adbc.hardcharger.global_setting.NAME` | `hardcharger.setting.NAME`, `hardcharger.global_setting.NAME` |
| `adbc.warp.*` | as `adbc.chargewire.*` above |

The Chargewire driver (`chargewire-adbc` 2.5.0) renamed its options the same way, to
`chargewire.*` (`chargewire.query.timeout_seconds`, `chargewire.ipc.compression`, ...).

## Upgrading from 2.2

Hardcharger's protocol is now named Chargewire. The server answers at `/chargewire` and
`/chargewire/v1/...`, and it keeps answering drivers and clients released before the rename in
the spelling they use.

- **Drivers and clients from 2.2 and earlier keep working** with the new server, unchanged,
  except that they show no column defaults (JDBC's `COLUMN_DEF`, for one): the server sends a
  column's default only under the Chargewire metadata key. Upgrade the driver to see them again.
- **The new drivers work with 2.2 servers too**, at the default base path, so servers and drivers
  can be upgraded in either order.
- **Connection strings keep working.** `hardcharger://` URIs, `jdbc:hardcharger://` URLs and the
  `adbc.hardcharger.*` options are unchanged (they were renamed later, in
  [hardcharger-adbc 2.7.0](#driver-option-names-hardcharger-adbc-270), and still work), and the drivers still read `warp://` URIs and
  `adbc.warp.*` option keys, as `chargewire://` and `adbc.chargewire.*`.
- **Single sign-on: register the new redirect URI before upgrading.** When
  [`oauth_redirect_uri`](/reference/configuration/#oauth_redirect_uri) isn't set, the server now
  sends `<oauth_base_url>/chargewire/v1/auth/oauth/callback` to the identity provider. Add that
  URL to the application's allowed redirect URIs (Okta, Microsoft Entra ID and Google all accept
  several), or set `oauth_redirect_uri` to the URL registered there today. The server answers its
  callback at both, so sign-in keeps working through the upgrade.
- **ODBC.** The Hardcharger ODBC Driver keeps its registered name, so its DSNs need no change. A
  DSN or connection string that names the generic Chargewire driver by its earlier registered
  name must name `Chargewire ODBC Driver` instead.
- **A proxy that routes by path** ([behind a load balancer](/guides/load-balancers/)) should pass
  `/chargewire/` as well as `/warp/`: new clients use the first, clients from before the rename
  the second.

## Rolling back

The installer keeps every version you installed, so switching back doesn't download anything:

```bash
curl https://install.hardcharger.gizmodata.com | HARDCHARGER_VERSION=<previous version> sh   # back
curl https://install.hardcharger.gizmodata.com | HARDCHARGER_VERSION=<newer version> sh      # and forward again
```

`--list` shows what is installed, the current version starred:

```console test server=none release
$ curl -s https://install.hardcharger.gizmodata.com | sh > /dev/null 2>&1
$ curl -s https://install.hardcharger.gizmodata.com | sh -s -- --list
Hardcharger versions in …/.hardcharger/versions:
  * … (current)
$ ~/.hardcharger/bin/hardcharger-server --version
Hardcharger …
```

`sh -s -- --uninstall 0.1.2` removes one version.

<Aside type="caution" title="Rolling back from 2.14">
A 2.13 or earlier server refuses an access-control store that 2.14 has upgraded. Restore the
store's backup from before the upgrade too ([Upgrading to 2.14](#upgrading-to-214)).
</Aside>

<Aside type="caution" title="Coming from GizmoSQL">
Moving from GizmoSQL 1.x is a migration, not an upgrade: new names, a new protocol and new
drivers. See [Coming from GizmoSQL](/get-started/coming-from-gizmosql/).
</Aside>
