Hardcharger runs DuckDB 2.0, so the SQL is DuckDB's: see [DuckDB's documentation](https://duckdb.org/docs/)
for the language itself. This page lists what Hardcharger adds. The function and setting tables
are generated from a running server (`duckdb_functions()`, `DESCRIBE`, `hardcharger_settings()`),
and CI fails when they drift.

## Settings

`SET [SESSION | GLOBAL] hardcharger.<name> = <value>` (or `TO`) and
`RESET [SESSION | GLOBAL] hardcharger.<name>`. `SET GLOBAL` needs an administrator; startup
settings can only be read, and say which option sets them.

```sql test
SET hardcharger.query_timeout = 60;
SELECT name, value, scope FROM hardcharger_settings() WHERE name = 'hardcharger.query_timeout';
RESET hardcharger.query_timeout;
```

## HUGEINT and UHUGEINT

DuckDB's 128-bit integers travel as Arrow `decimal128(38, 0)` by default, which every Arrow client
reads. That type holds at most 38 digits, so a value of 10<sup>38</sup> or more (a HUGEINT can reach
about 1.7 × 10<sup>38</sup>, a UHUGEINT twice that) can't be sent in it. Such a statement fails
with a conversion error that names the value, rather than sending a wrong number:

```console test exit=1
$ HARDCHARGER_PASSWORD='change-me' hardcharger --host localhost --tls=false --username hardcharger --csv \
    --command "SELECT 170141183460469231731687303715884105727::HUGEINT AS big"
Error: Conversion Error: Hardcharger cannot send the HUGEINT value 170141183460469231731687303715884105727 as Arrow decimal128(38, 0), which holds at most 38 digits. CAST it to VARCHAR, or run SET SESSION arrow_lossless_conversion = true (DuckDB's 16-byte HUGEINT Arrow type, which holds every value)
```

Every value that fits is sent exactly as before. For the others, either `CAST` to `VARCHAR`:

```console test
$ HARDCHARGER_PASSWORD='change-me' hardcharger --host localhost --tls=false --username hardcharger --csv \
    --command "SELECT CAST(170141183460469231731687303715884105727::HUGEINT AS VARCHAR) AS big"
big
170141183460469231731687303715884105727
```

or turn on `arrow_lossless_conversion` for the session, which sends DuckDB's own 16-byte Arrow
types (an `arrow.opaque` extension type over `fixed_size_binary(16)`, little-endian) that hold every
value, and decode them in the client. It also changes how UUID and JSON columns are sent.

```python test
from adbc_driver_hardcharger import dbapi as hardcharger

with hardcharger.connect(uri="hardcharger://localhost?tls=false", username="hardcharger", password="change-me") as conn:
    with conn.cursor() as cur:
        cur.execute(operation="SET SESSION arrow_lossless_conversion = true")
        cur.execute(operation="SELECT 340282366920938463463374607431768211455::UHUGEINT AS biggest")
        raw = cur.fetchone()[0]
        print(int.from_bytes(raw, byteorder="little", signed=False))
```

```text output
340282366920938463463374607431768211455
```

The [`hardcharger` CLI](/clients/cli/) decodes them for you: with the option on, it prints exact
integers in every output mode.

```console test
$ HARDCHARGER_PASSWORD='change-me' hardcharger --host localhost --tls=false --username hardcharger --csv --quiet \
    --command "SET SESSION arrow_lossless_conversion = true; SELECT 340282366920938463463374607431768211455::UHUGEINT AS biggest"
OK
biggest
340282366920938463463374607431768211455
```

Write `SET SESSION`: a plain `SET arrow_lossless_conversion` is DuckDB's global setting, which
changes every session's results and needs an administrator (`MANAGE CONFIG` under access
control). Over [plain HTTP](/clients/http/), the Warp SQL session option
`duckdb_arrow_lossless_conversion` does the same for one session. JSON bind parameters beyond the
64-bit range bind exactly as HUGEINT or UHUGEINT; wider ones are refused.

## KILL SESSION

```sql
KILL SESSION '<session id>';
```

Ends another session at once (administrators only); its next request gets `401 session_ended`
with reason `killed`.
`hardcharger_sessions()` lists the ids. See [Statement control](/guides/statement-control/#kill-a-session).

## Access-control statements

With [access control](/guides/access-control/) on, these run like SQL, one per statement:

| Statements | Guide |
|---|---|
| `CREATE`/`ALTER`/`DROP USER`, `CREATE`/`DROP ROLE`, `GRANT role TO`, `REVOKE role FROM` | [Users, roles and grants](/guides/access-control/) |
| `GRANT`/`REVOKE` privileges `ON` table, view, `SCHEMA`, `CATALOG`; system privileges | [Users, roles and grants](/guides/access-control/#privileges) |
| `SHOW GRANTS`, `ALTER TABLE`/`VIEW … OWNER TO`, `SET ROLE` | [Users, roles and grants](/guides/access-control/#seeing-grants) |
| `CREATE`/`DROP ROW POLICY`, `SHOW ROW POLICIES` | [Row policies](/guides/row-policies-and-masking/#row-policies) |
| `CREATE`/`DROP MASKING POLICY`, `ALTER TABLE … MODIFY COLUMN … SET`/`UNSET MASKING POLICY`, `SHOW MASKING POLICIES` | [Masking](/guides/row-policies-and-masking/#masking-policies) |
| `CREATE`/`DROP TENANT`, `ALTER CATALOG … SET TENANT`, `ALTER TENANT … SET DEFAULT CATALOG`, `SHOW TENANTS` | [Tenants](/guides/row-policies-and-masking/#tenants) |
| `CREATE`/`DROP GROUP MAPPING`, `SHOW GROUP MAPPINGS` | [SSO](/guides/sso/#with-access-control-users-and-group-mappings) |
| `CREATE`/`DROP SCOPED TOKEN`, `SHOW SCOPED TOKENS` | [Scoped tokens](/guides/row-policies-and-masking/#scoped-tokens) |

Row policies may call `session_attribute('key')` (a user attribute set with
`ALTER USER … SET ATTRIBUTE`) and `is_role_active('role')`.

## System catalogs

| Catalog | Contents |
|---|---|
| `_hardcharger_system` | Read-only views the drivers use: `hardcharger_index_info` (JDBC `getIndexInfo`) and `hardcharger_view_definition` |
| `_hardcharger_instr` | [Instrumentation](/guides/instrumentation-and-audit/) (with `--enable-instrumentation`; administrators only) |
| `_hardcharger_logs` | [Catalog logging](/guides/instrumentation-and-audit/#catalog-logging) (with `--enable-catalog-logging`; administrators only) |

Nobody writes to, detaches or `USE`s these catalogs.
